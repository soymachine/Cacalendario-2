2. Preparación (una sola vez)

  1. Cuentas: cuenta de Expo con acceso a los dos proyectos, Apple Developer Program (para cualquier build de iOS en dispositivo) y Google Play Console con las apps com.fluxiahealth.app y com.fluxiahealth.medics creadas.
  2. EAS CLI instalado y con sesión iniciada: 
    npm install -g eas-cli
eas login
eas whoami          # comprueba con qué cuenta estás
  3. Credenciales: deja que EAS gestione certificados de iOS y keystore de Android. La primera vez que hagas un build te preguntará; acepta "Let EAS handle it". Para revisarlas: eas credentials.
  4. Clave de Google Play para eas submit (opcional, para subir a Play desde la terminal): en Google Cloud crea una service account, descarga su clave JSON y dale acceso en Play Console → Usuarios y permisos (permiso de publicar en tracks de prueba). Guárdala fuera del repo (p. ej. ~/keys/fluxia-play.json); nunca la subas a git.

3. Antes de cada build

  1. Trae lo último de main: 
    git checkout main && git pull
  2. Instala dependencias y comprueba que compila (desde mobile/ o mobile-medics/): 
    cd mobile               # o: cd mobile-medics
npm ci
npx tsc --noEmit
npx expo export --platform ios
  3. Módulos nativos alineados: todos los expo-* deben ir en la misma revisión del SDK. Si alguien ha añadido uno nuevo, sube primero expo a la última revisión y alinea el resto, o la app se cerrará al abrirse: 
    npm install expo@~57.0.x
EXPO_OFFLINE=1 npx expo install --fix
  4. Backend primero: si la versión necesita migraciones de Supabase o Edge Functions nuevas, aplícalas y despliégalas antes de distribuir la app.
  5. Versión: si vas a publicar una versión nueva en las tiendas, sube "version" en app.json (ver sección 7) y haz commit.

4. Prueba interna (sin pasar por las tiendas)

Android APK instalable

eas build --platform android --profile preview

Al terminar, EAS muestra un enlace y un QR. Ábrelo en el móvil Android, descarga el APK e instálalo (Android pedirá permitir "instalar apps de orígenes desconocidos" para el navegador). Puedes compartir ese mismo enlace con los testers.

iOS Build ad hoc para iPhones concretos

  1. Registra cada iPhone que vaya a instalarla (solo la primera vez por dispositivo): 
    eas device:create
    Genera un enlace o QR: se abre en el iPhone y se instala un perfil. Para ver los registrados: eas device:list.
  2. Lanza el build: 
    eas build --platform ios --profile preview
  3. Abre el enlace del build en el iPhone e instala.
El build solo se puede instalar en los iPhones registrados antes de lanzarlo. Si añades un dispositivo después, tienes que volver a hacer el build. Para más de 2-3 personas suele ser más cómodo usar TestFlight con testers internos.

5. TestFlight (iOS)

  1. Build de producción (EAS sube solo el número de build): 
    eas build --platform ios --profile production
  2. Envíalo a App Store Connect: 
    eas submit --platform ios --latest
    La primera vez pedirá iniciar sesión con tu Apple ID y elegir la app de App Store Connect. Puedes hacer los dos pasos de una vez con: 
    eas build --platform ios --profile production --auto-submit
  3. En App Store Connect → tu app → TestFlight, espera a que el build pase de "Procesando" a disponible (normalmente 10-30 min). La pregunta de cifrado ya está respondida en app.json (ITSAppUsesNonExemptEncryption: false), así que no debería pedir nada.
  4. Testers internos (miembros de tu equipo de App Store Connect, hasta 100): añádelos al grupo interno y reciben el build al momento, sin revisión.
    Testers externos (cualquier email, hasta 10.000): crea un grupo externo y añade el build; el primer build de cada versión pasa una revisión beta de Apple (normalmente menos de 1 día).
  5. Los testers instalan la app TestFlight desde la App Store y aceptan la invitación.
Para publicar en la App Store: en App Store Connect crea la versión (mismo número que "version" de app.json), selecciona el build ya probado en TestFlight y envíalo a revisión.

6. Google Play

  1. Build de producción (genera un .aab): 
    eas build --platform android --profile production
  2. La primera vez que se sube cada app, Google exige hacerlo a mano: descarga el .aab desde el enlace del build y súbelo en Play Console → tu app → Pruebas → Prueba interna → Crear versión.
  3. Las siguientes veces puedes subirlo desde la terminal con la clave de la service account: 
    eas submit --platform android --latest
    Para no tener que indicar la clave y el track cada vez, puedes añadir esto a eas.json (en submit.production), con la ruta a tu clave fuera del repo: 
    "submit": {
  "production": {
    "android": {
      "serviceAccountKeyPath": "../../keys/fluxia-play.json",
      "track": "internal"
    }
  }
}
  4. En Play Console, en Prueba interna → Testers, añade la lista de emails y comparte el enlace de participación. Los testers instalan desde Google Play; la prueba interna está disponible en minutos y no pasa revisión.
  5. Para ir a producción: Promocionar versión de prueba interna a prueba cerrada o directamente a Producción, y enviar a revisión.
Si es una cuenta de desarrollador personal creada después de noviembre de 2023, Google exige una prueba cerrada con al menos 12 testers durante 14 días antes de poder publicar en producción. La prueba interna no cuenta para este requisito.

7. Versiones y números de build

QuéDóndeQuién lo cambia
Versión visible (p. ej. 0.90.0)"version" en app.jsonTú, a mano, cuando publicas una versión nueva en las tiendas
Número de build (iOS buildNumber, Android versionCode)En los servidores de EAS (appVersionSource: "remote")EAS, automáticamente en cada build production (autoIncrement)

Varios builds de la misma versión (p. ej. 0.90.0 build 7, 8, 9) son normales mientras pruebas en TestFlight o en la prueba interna. Ver o corregir el número de build:

eas build:version:get
eas build:version:set     # si alguna vez se desincroniza con la tienda

8. Problemas frecuentes

SíntomaCausa y solución
La app se cierra nada más abrirse (en el log: dyld … Symbol not found … ExpoModulesCore)Módulos expo-* de revisiones distintas del SDK. Alinéalos (paso 3 de sección 3) y vuelve a hacer el build.
Play Console rechaza el .aab por "código de versión ya usado"El número de build de EAS va por detrás del de la tienda. Súbelo con eas build:version:set por encima del último de Play.
eas submit -p android falla en la primera subidaGoogle no deja usar la API hasta que hay al menos una subida manual. Sube el primer .aab a mano (sección 6).
Un iPhone no puede instalar el build previewNo estaba registrado cuando se hizo el build. eas device:create y repite el build.
No llegan notificaciones push en PAPrueba con un build preview o production (en Expo Go no funcionan). En Android hace falta google-services.json (ya está en mobile/) y las credenciales FCM en eas credentials. Revisa la pestaña Notificaciones de /admin.
